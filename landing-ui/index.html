ScaleGuard is the open-source application gateway that replaces your load balancer, reverse proxy, certificate client, WAF, rate limiter, DNS server and tunnels. Run it with one command, then manage everything live from a web UI.

$ curl -fsSL https://scaleguard.dev/install.sh | sh
$ ./scaleguard-docker.sh
$ ./scaleguard-docker.sh up --postgres

Then open http://localhost:8080/adminui/. A strong admin password is generated for you, there is no default login.

Why ScaleGuard

Putting a service on the internet shouldn't take eight tools.

A load balancer, a proxy, a certificate client, a WAF, a rate limiter, a DNS provider, a log stack and a tunnel: each with its own config, its own reload and its own way to break. ScaleGuard is all of them in one process, configured live, with no config files.

  1. Chapter 1

    Monday: fourteen tools, fourteen ways in.

    Northbeam is a 40-person product team. Over three years it has collected a metrics dashboard, an admin panel, a staging API, a wiki and a CI server. Each one lives on its own port, has its own login (or none), and its own expiring certificate. Last week someone pasted a tunnel link to a demo into Slack. Nobody can say, with confidence, what is reachable from the internet.

    The problem isn't any single tool. It's that there is no single place to look.

  2. Chapter 2

    One front door.

    They install ScaleGuard on one small server with a single command and map each app to a name with Quick Mapping: metrics.tools.example.com, admin.tools.example.com and so on. HTTPS certificates are ordered and renewed automatically. ScaleGuard can even host the DNS zone itself, so the names resolve to the gateway and nothing else. The apps stop listening to the world; only the gateway talks to them.

    Result: one list of everything exposed, all on HTTPS, in the admin UI.

  3. Chapter 3

    Only the right people and services.

    Each route gets its own allow-list: the office and VPN ranges for the human tools. The partner that calls the staging API gets an OAuth 2.0 client with a scope for that route and nothing else, so its token can be revoked without touching anyone else. The admin API itself needs a token and has its own limit so a mistake can't lock the admins out.

    Access is a setting on the route, not a convention people remember.

  4. Chapter 4

    Even internal apps get protected.

    Internal doesn't mean safe: scanners find forgotten hostnames in hours, and a runaway script can hammer a staging database as hard as an attacker. The WAF runs per route with the OWASP rule set, a token bucket limits every client, and noisy addresses can be blocked for an hour with one click. Static pages like the wiki are cached so they survive a rush.

    Abuse gets a 403 or 429 at the door, and the app behind it never sees it.

  5. Chapter 5

    Sharing a laptop demo, safely.

    Sam needs to show a prototype to a colleague. Instead of an anonymous tunnel link, Sam runs safeexpose 3000 demo. The prototype appears at demo.tools.example.com as a normal route, behind the same HTTPS, allow-list and WAF as everything else. When Sam presses Ctrl+C the route is removed. If the Wi-Fi drops, it reconnects by itself.

    Temporary doesn't have to mean uncontrolled.

  6. Chapter 6

    Glue without another server.

    The team needs a small status endpoint and a webhook that fans a message out to chat. Rather than deploy and secure two more services, they write them as cloud functions in the admin UI. The functions run in a sandbox, may only call the hosts the admin allows, read only the secrets the admin ticks, and inherit the route's rules and cache.

    A new endpoint is ten lines of code and a route, not a new thing to patch.

  7. Chapter 7

    Seeing everything, and staying up.

    Every request is recorded in the built-in analytics with a trace ID: who called what, how long it took, what was blocked. A question like "which client hit the admin panel at 3 a.m.?" is a SQL query, not an archaeology project. A second node joins the first so the front door survives a restart, and configuration stays identical on both without a shared database.

    One place to see what is exposed. One place to change it. Every request on the record.

Flagship · SafeExpose

Put any app on the internet with one command.

SafeExpose is the open-source, self-hosted alternative to ngrok that ships with ScaleGuard. It publishes a service from your laptop or a private network at your own domain, with automatic HTTPS, through the same gateway that protects the rest of your infrastructure.

  • One command. safeexpose 3000 and your local app is live. Name it with safeexpose 3000 demo.
  • Your domain, your certificate. No random URLs, no vendor account, no request quotas.
  • Controlled. Tunnels are normal routes, so allow-lists, WAF, rate limits and analytics apply. Ctrl+C removes the route.
  • Built to stay up. Reconnects with back-off after Wi-Fi changes and sleep, re-creates the tunnel if the server restarted, and dev-server hot reload (WebSockets) works.

Fully open source, MIT. Client and server are both on GitHub. Read it, fork it, run it on your own infrastructure. github.com/dhaneeshtb/scalegurad-safeexpose

Everything included

Everything included. Nothing bolted on.

Nothing here is a plugin, a paid tier or a separate service. It is all in the same open-source build.

Load balancing & reverse proxy

Round-robin, least-connections, weighted and active/standby. Route by host, port, path, header or JWT claim. HTTP/1.1, HTTP/2, HTTP/3 over QUIC, gRPC with streaming, WebSockets and raw TCP, with active and passive health checks, connect retries and per-service timeouts.

Web application firewall

21 built-in rules plus your own, OWASP Core Rule Set import with anomaly scoring, per-route policies and a dry-run tester. 44 of 44 attacks blocked, 37 of 37 legitimate requests allowed in the test suite.

Rate limiting & IP rules

Token bucket per client and route with 429 + Retry-After, spoof-proof behind proxies, one budget across the whole cluster, plus allow/deny lists and timed blocks.

Automatic HTTPS

Let's Encrypt certificates ordered and renewed for every route (HTTP-01 or DNS-01), chosen per connection by SNI. Add a route and it is on HTTPS.

Authoritative DNS

Host your zones on the gateway: A, AAAA, CNAME, TXT, MX, NS, rate limiting and caching forwarders. Served domains answer with the IPs of every connected node.

SafeExpose tunnels flagship

A fully open-source, self-hosted ngrok alternative. safeexpose 3000 publishes a service from a laptop or private network at your domain, with HTTPS, and survives network drops. See how.

Analytics you can query

Every request lands in an embedded DuckDB: live dashboards for traffic, status classes, p50/p95 latency, top routes and blocked attacks, searchable access logs with CSV/NDJSON export, a read-only SQL console and W3C traceparent support. No log stack to run.

Active-active clustering with DR

Every node serves traffic. Nodes elect a master by majority vote and keep identical configuration through a SHA-256-chained ledger, with no shared database. A new master in about three seconds, and a standby site you promote with one call. Break a node and watch.

Cloud functions

Answer a route with a sandboxed Groovy function instead of running a server. headers, query and the parsed body are variables; auth, rate limits, WAF and caching come from the route. See an example.

Cloud functions

Answer a route with code, not a server.

Write a small Groovy function in the admin UI and attach it to any route. headers, query and the parsed body are just variables. It inherits the route's auth, rate limit, WAF, CORS and caching, and runs in a sandbox.

  • Sandboxed. No files, processes, reflection or threads; hard time, memory and size limits.
  • You set the permissions. Outbound calls are off until you allow them, with host allowlists and SSRF protection.
  • Scales and replicates. Compiled once, bounded concurrency, hot reload, synced across the cluster.
  • Test in the UI. Sample request panel, run logs and ready-made examples.

Functions share the gateway's JVM, so treat authors as trusted staff. Read exactly what the sandbox does and does not guarantee.

weather.groovy · GET /weather?lat=9.93&lon=76.26
// headers, query and body are ready-made variables
def r = http.get(
  "https://api.open-meteo.com/v1/forecast" +
  "?latitude=${query.lat}&longitude=${query.lon}" +
  "&current=temperature_2m")

if (!r.ok) {
  return res.status(502).json([error: 'upstream ' + r.status])
}
return [temperature: r.json().current.temperature_2m]

High availability & disaster recovery

Active-active by default. A second site on standby.

Run three ScaleGuard nodes and every one of them serves traffic. They elect a master by majority vote and keep identical configuration through a tamper-evident ledger, with no shared database, no etcd, no ZooKeeper. Add a standby site in another region and you can fail over to it with one call.

Times shown are measured on local test clusters (3 primary nodes plus a 2-node DR site): a new master after kill -9 in 2.9–3.8 s, and a promoted DR site electing its master in 3.7 s. See the full list of tested behaviour.

Every node serves traffic

Put any load balancer, DNS round robin or anycast in front. Each node proxies requests on its own, so adding a node adds capacity and losing one costs only its share.

A ledger instead of a database

Every configuration change is appended to a SHA-256 hash chain on every node. Copies are verified link by link, a tampered entry is refused, and a Verify chains button checks it all.

No split brain

A master needs a majority. If the minority side of a network split cannot reach one, it stops accepting changes while it keeps serving traffic, so the two halves can never diverge.

Disaster recovery in one call

A DR site copies every change and the cluster's analytics, serves traffic, and follows the primary master without ever standing for election. If the primary site is lost it refuses changes with a clear "promote" hint rather than guessing. POST /cluster/dr/promote (or one button) makes it the primary, and old nodes that return follow the new master. Promotion refuses to run while the primary still answers, unless you force it.

Shared where it matters

Rate-limit budgets are shared across nodes (strict mode admitted 2,202 requests against an ideal of 2,200). Refresh tokens are redeemed on the master, so a token cannot be used twice on two nodes. Analytics from every node are collected, so any node can answer for the whole cluster within seconds.

Set it up in three commands

  • Same admin login on every node. Nodes call each other with tokens signed from it.
  • Use an odd number of voting nodes, 3 or more. With two, losing one pauses changes (traffic still flows).
  • DR nodes list the primary nodes as peers and add one flag. Primary nodes learn about them by gossip.
  • Docker? Pass the same flags in SCALEGUARD_EXTRA_OPTS.
# three active-active nodes: each lists the other two
$ java -Dport=80 -Dscaleguard.nodeName=a \
    -Dscaleguard.cluster.advertise=http://10.0.0.10:80 \
    -Dscaleguard.cluster.peers=10.0.0.11:80,10.0.0.12:80 \
    -DadminUser=admin -DadminPassword=… -jar scaleguard.jar

# a DR node in another region
$ java … -Dscaleguard.cluster.dr=true \
    -Dscaleguard.cluster.advertise=http://10.1.0.10:80 \
    -Dscaleguard.cluster.peers=10.0.0.10:80,10.0.0.11:80,10.0.0.12:80 \
    -jar scaleguard.jar

# after losing the primary site
$ curl -X POST http://10.1.0.10/cluster/dr/promote?scaleguard=true

Questions

Frequently asked questions.

What is ScaleGuard?

ScaleGuard is a free, open-source, self-hosted application gateway. In one Java process it provides a load balancer and reverse proxy, a web application firewall, rate limiting, automatic HTTPS certificates, an authoritative DNS server, SSH tunnels, request analytics and cloud functions, and it is configured live from a web UI or REST API.

How do I install ScaleGuard?

On macOS or Linux run curl -fsSL https://scaleguard.dev/install.sh | sh. With Docker, clone the repository and run ./scaleguard-docker.sh. Both give you an admin UI at /adminui and generate an admin password, because there is no default login.

What does ScaleGuard need to run?

Java 21 or newer, or Docker. It runs as a single JAR on a laptop, a virtual machine or a container. The configuration store is SQLite by default and can be PostgreSQL; the response cache and analytics use embedded DuckDB, so there is no other server to run.

Is ScaleGuard free?

Yes. ScaleGuard is open source under the MIT license, with no paid tier, and every feature described on this page is in the open-source build.

How does ScaleGuard compare with NGINX and HAProxy?

In one-core benchmarks on small responses ScaleGuard reached about 93% of NGINX throughput and more than twice Envoy. NGINX and HAProxy are ahead on tail latency, memory use and decades of hardening. ScaleGuard adds a built-in web UI, WAF, analytics, DNS, tunnels, clustering and cloud functions that those proxies need extra modules, plugins or paid tiers for.

Can I use ScaleGuard to control internal apps and tools?

Yes. Put dashboards, admin panels, staging APIs and wikis behind one ScaleGuard front door: each gets a named HTTPS route, per-route IP allow-lists, scoped OAuth 2.0 tokens for service clients, a web application firewall, rate limits and a recorded request log. SafeExpose publishes laptop demos through the same rules, and cloud functions replace small helper services. ScaleGuard limits human access by network address and API access by tokens; it is not a single-sign-on provider for people.

Is ScaleGuard an ngrok alternative?

Yes. SafeExpose is a fully open-source (MIT) self-hosted alternative to ngrok that works with ScaleGuard. It publishes a service from a laptop or private network at your own domain over an SSH tunnel with automatic HTTPS, using one command such as safeexpose 3000. It reconnects automatically when the network drops, and its code is on GitHub at dhaneeshtb/scalegurad-safeexpose.

Does ScaleGuard support HTTP/3 and gRPC?

Yes. HTTP/3 over QUIC is served on every HTTPS port alongside HTTP/2 and HTTP/1.1, and gRPC unary and streaming calls are proxied message by message. Each protocol can be switched off per route.

Can ScaleGuard run as a cluster?

Yes. Run three or more nodes and every one serves traffic (active-active). They elect a master by majority vote, keep identical configuration through a SHA-256 hash-chained ledger without a shared database, and share rate-limit budgets. In local test clusters a new master was elected 2.9 to 3.8 seconds after the old one was killed. A disaster-recovery standby site copies every change and can be promoted with one call. PostgreSQL mode is also available.

What happens if a node or a whole data centre fails?

If a node fails, the other nodes keep serving traffic, and if it was the master the rest elect a new one in a few seconds. If the whole primary site is lost, the disaster-recovery site keeps serving traffic on the configuration it has, but refuses configuration changes with a hint to promote it, so the two sites can never diverge. Promoting the DR site (one API call or button) makes it the primary, and old nodes that come back follow the new master. A minority side of a network split stops accepting changes but keeps serving traffic.

Are ScaleGuard cloud functions safe?

Cloud functions are Groovy scripts that run in a layered sandbox with no file, process, reflection or thread access, hard time, memory and size limits, and outbound network calls switched off unless the admin enables them with an allowlist and SSRF protection. They share the JVM, so they are not a hard security boundary and should be written by trusted people.
